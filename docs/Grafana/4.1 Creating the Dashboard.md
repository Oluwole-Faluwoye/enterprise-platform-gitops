# 4.1 Building Panel 1 – Requests per Second (Requests/sec)

---

# Objective

The first panel created in the Enterprise Platform Overview dashboard displays the current number of HTTP requests processed by the `auth-service` every second.

This panel provides an immediate indication of application traffic and serves as one of the primary indicators used during monitoring and load testing.

Unlike CPU or memory utilization, request throughput measures how much work the application is performing rather than how many resources it is consuming.

During later load testing with k6 (covered in Chapter 9), this panel becomes one of the most important metrics because it confirms whether traffic is successfully reaching the application.

---

# Why This Metric Matters

A sudden increase in Requests/sec generally indicates:

- Increased user traffic
- Load testing in progress
- Background jobs generating requests
- Traffic spikes

A sudden drop to zero may indicate:

- Application failure
- Failed deployment
- Kubernetes Service issues
- Ingress routing issues
- DNS problems
- Prometheus scrape failures

This panel should therefore be one of the first metrics checked during incident response.

# PromQL Query

Paste the following query exactly as shown.

```promql

```

This is the exact query used during implementation.

After pasting the query,

```

```

If Prometheus is successfully scraping the application, the preview panel immediately updates.

---

# Understanding the Query

This query consists of three parts.

```
http_server_requests_seconds_count
```

This Micrometer metric counts every HTTP request handled by the application.

Example

```
Request 1

↓

Counter = 1

Request 2

↓

Counter = 2

Request 3

↓

Counter = 3
```

The counter continuously increases.

Displaying the raw counter would not be useful because it never decreases.

Instead,

Prometheus calculates the rate of increase.

---

## rate()

```
rate(metric[5m])
```

Calculates the average increase per second during the last five minutes.

Example

```
500 requests

↓

550 requests

↓

50 requests over 5 minutes

↓

0.166 requests/sec
```

This provides a stable measurement of traffic.

---

## Why Use Five Minutes?

Initially, shorter windows such as

```
1m
```

were considered.

However,

a five-minute range produces smoother graphs and avoids large spikes caused by short traffic bursts.

Five minutes is commonly used for operational dashboards.

---

## Why Use sum()?

The Enterprise Platform will eventually scale horizontally using the Horizontal Pod Autoscaler (HPA).

Each Pod exposes its own request counter.

Example

```
Pod A

15 req/sec

Pod B

18 req/sec

Pod C

22 req/sec
```

Without

```
sum()
```

Grafana would display three separate values.

Using

```promql
sum(rate(...))
```

combines all Pods into a single platform-wide request rate.

This makes the dashboard easier to interpret.

# Troubleshooting

## Problem

The panel displays:

```
No Data
```

### Possible Causes

- Prometheus is not scraping the application.
- The datasource is not Prometheus.
- The `job` label is incorrect.
- No requests have reached the application.
- The application is not exposing Actuator metrics.

---

## Verify Scraping

Execute:

```promql
up
```

Expected:

```
auth-service
```

should appear with the value:

```
1
```

If the target does not appear,

refer to Chapter 8.

---

## Verify Metric Availability

Execute:

```promql
http_server_requests_seconds_count
```

If no series are returned,

verify that:

- Spring Boot Actuator is enabled.
- Micrometer Prometheus registry is installed.
- `/actuator/prometheus` is accessible.

# Lessons Learned During Implementation

During the initial implementation,

this panel displayed:

```
No Data
```

Investigation revealed that Prometheus was **not** scraping the `auth-service`.

The root cause was not the PromQL query.

Instead,

the Kubernetes `ServiceMonitor` selector did not match the labels defined on the `auth-service` Service.

Because the labels did not match,

Prometheus never discovered the application.

Once the Service labels and ServiceMonitor selector were aligned,

Prometheus immediately began scraping metrics,

and the panel started displaying request throughput.

This troubleshooting process is documented in detail in Chapter 8.

# Interview Talking Points

An interviewer may ask:

> Why did you choose Requests/sec as the first panel?

Example response:

> Requests/sec is one of the most important operational metrics because it immediately indicates whether traffic is reaching the application. During deployments or load testing, I can quickly verify that requests are flowing through the platform. Since the query aggregates metrics across all Pods using `sum(rate(...))`, it continues to provide an accurate platform-wide view even after horizontal scaling.

---

# Summary

The Requests/sec panel provides a real-time view of application throughput.

It was intentionally placed at the top of the Enterprise Platform Overview dashboard because it answers one of the first operational questions:

> Is the platform receiving traffic?

The next panel builds on this metric by measuring not how many requests are processed, but how long they take to complete.
