# 4.3 Building Panel 2 – Average Response Time

---

# Objective

The second panel created for the Enterprise Platform Overview dashboard measures the average HTTP response time of the `auth-service`.

Unlike the Requests/sec panel, which measures application throughput, this panel measures application performance.

During normal operation, an application may process thousands of requests per second while still responding very quickly. Conversely, an application may process only a few requests per second but respond very slowly due to inefficient code, database latency, or infrastructure bottlenecks.

For this reason, request throughput and response latency should always be monitored together.

This panel answers the operational question:

> **How quickly is the application responding to incoming requests?**

---

# Why This Metric Matters

Response time is one of the most important indicators of application performance.

High response times may indicate:

- Database bottlenecks
- Slow API integrations
- JVM garbage collection pauses
- CPU saturation
- Memory pressure
- Network latency
- Thread pool exhaustion
- Poor application performance

During load testing, this panel is often monitored alongside CPU Usage and Requests/sec to determine whether increasing traffic is affecting application responsiveness.

# Understanding the Query

This query calculates the average duration of HTTP requests.

Micrometer exposes two related metrics:

```
http_server_requests_seconds_sum
```

The cumulative amount of time spent processing HTTP requests.

Example

```
Request 1

0.20 seconds

Request 2

0.40 seconds

Request 3

0.60 seconds

Total

1.20 seconds
```

---

The second metric is

```
http_server_requests_seconds_count
```

which counts how many requests have been processed.

Example

```
Request Count

3
```

---

By dividing

```
Total Request Time

/

Number of Requests
```

Prometheus calculates the average response time.

Mathematically,

```
Average Latency

=

Total Processing Time

/

Total Requests
```

This provides a continuously updated average latency.

---

# Why Use rate()

Both metrics are cumulative counters.

Without

```
rate()
```

the values increase forever.

Using

```promql
rate(metric[5m])
```

calculates the rate of change over the previous five minutes.

This provides a stable moving average.

---

# Why Five Minutes?

The five-minute window was selected because it balances responsiveness with stability.

Smaller windows may fluctuate significantly during periods of low traffic.

Longer windows react too slowly to production issues.

Five minutes is commonly used for operational dashboards.

# Interpreting Results

The following table provides general guidance.

| Average Response Time | Interpretation |
|----------------------|----------------|
| < 100 ms | Excellent |
| 100–300 ms | Good |
| 300–500 ms | Acceptable |
| 500–1000 ms | Investigate |
| > 1 second | Critical |

These thresholds are general guidelines and should be adjusted based on application requirements.

# Troubleshooting

## Problem

The panel displays

```
No Data
```

### Possible Causes

- Prometheus is not scraping the application.
- Incorrect datasource selected.
- Incorrect `job` label.
- No HTTP requests have been processed.
- Spring Boot Actuator metrics are unavailable.

---

## Verify Metric Availability

Execute:

```promql
http_server_requests_seconds_sum
```

If no series are returned,

verify:

- Micrometer Prometheus Registry is installed.
- Spring Boot Actuator is enabled.
- `/actuator/prometheus` is accessible.

---


# Lessons Learned During This Project

During implementation,

this panel initially displayed

```
No Data
```

The PromQL query itself was correct.

The root cause was that Prometheus had not discovered the `auth-service` because the `ServiceMonitor` selector did not match the labels defined on the Kubernetes Service.

After correcting the label mismatch, Prometheus immediately began scraping metrics and the panel displayed valid response time values.

This issue is documented in detail in Chapter 8.

# Interview Talking Points

An interviewer may ask:

> Why did you calculate average response time using two Prometheus metrics?

Example response:

> Micrometer exposes request duration as cumulative counters rather than direct averages. To calculate the average response time, I divided the rate of the cumulative request duration (`http_server_requests_seconds_sum`) by the rate of the cumulative request count (`http_server_requests_seconds_count`). Using `rate()` converts both counters into per-second rates over a five-minute window, allowing Grafana to display a continuously updated moving average of request latency.
